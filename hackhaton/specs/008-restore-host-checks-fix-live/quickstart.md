# Quickstart — 008 acceptance walk-through

**Audience**: anyone reviewing or demoing 008
**Date**: 2026-05-11
**Estimated time**: 10 minutes end-to-end against a real testbed

This walkthrough drives every acceptance scenario in `spec.md` once,
in order, with the exact commands and expected results.

---

## Prerequisites

1. Working tree on this branch (`008-restore-host-checks-fix-live`),
   build artefacts current.
2. `ree-vehicle-configs` and `ree-reecu` clones present at the
   paths `~/.config/vayobd/settings.toml` points to.
3. SSH config (`~/.ssh/config`) with a working entry for at least
   one in-scope TS host (e.g. `ts-de-ber-00005` or
   `ts-de-ber-zeus`).
4. The .deb installed at `dist/vayobd_0.0.X_amd64.deb` (any 0.0.6+
   build will work); `/usr/bin/vayobd --version` succeeds.

## Step 6 — Manual end-to-end against the installed .deb

```bash
# Run the .deb-installed binary (full path bypasses any pyenv shim).
/usr/bin/vayobd run

# Open http://127.0.0.1:8000 in your browser.
```

Verify against US1 acceptance scenarios:

1. **Pick a reachable TS host through the wizard.** Within 10 s of
   landing on the detail page, you should see:
   - The version card at the top with vDrive / vREECU / SEC
     resolved (live values + verdict pills + as-of timestamps +
     source pill + refresh button — all 007's UI intact).
   - The check battery below: a "Working" group with the passing
     checks (e.g. SSH reachable, network reachable) and a "Needs
     attention" group with any failing ones (e.g. Peplink VPN if
     a tunnel is down).
   - Repair-guide buttons next to failed items where a guide is
     registered (harness diagram, WAKE signal-path, etc.).
2. **Click a repair-guide button.** Confirm it opens as a SHEET
   over the page (not a route change) — the version card remains
   visible behind it.
3. **Click the Refresh button on the version card.** Confirm:
   - Both pipelines re-run with `?fresh=true`.
   - All three version cells go back to loading (em-dash + spinner)
     until the response lands.
   - The check battery either re-runs alongside OR keeps its prior
     result — never silently disappears.
4. **Navigate away and back within 60 s.** The page renders the
   cached values instantly (no spinner, no engine call).

Verify against US2 acceptance scenarios:

5. **Toggle Developer mode on.** Confirm BOTH "Live diagnostic"
   buttons appear (header + main page primary-action area).
6. **Click the header copy.** Lands on `/live`. The page mounts,
   the connection dialog renders, the inventory list populates,
   no console errors, no 4xx/5xx on any request.
7. **Pick a reachable TS host, click Connect.** Within 10 s,
   decoded CAN signals stream into the state panel. If the local
   `ree-reecu` clone is incomplete, the errq panel shows a clear
   degraded-mode message (per 004 FR-012) — but the rest of the
   surface (decoded signals + raw frames log) keeps working.

Verify against US4 (no 007 regressions):

8. **Toggle Developer mode off.** Confirm both Live diagnostic
   buttons disappear together. Direct navigation to `/live` still
   redirects to the picker (007's gate intact).
9. **Read any user-facing string anywhere on the page.** Confirm
   no literal `strings.xxx.yyy` path keys appear. No "Run check
   against this host" copy in places where it's stale (the picker
   subtitle reverts to its pre-007 wording per
   contracts/strings-merge.md § 4, which IS correct now that the
   restored battery makes "running a check" the action again).
